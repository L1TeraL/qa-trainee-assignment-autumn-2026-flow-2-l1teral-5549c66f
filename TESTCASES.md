# Test Cases

## 1. Регистрация

### REG-001 — Успешная регистрация

* **Тип:** Positive, Functional
* **Предусловия:** Пользователь с таким username не зарегистрирован.
* **Шаги:**

  1. Отправить `POST /api/1/register`.
  2. Передать уникальный `username` и корректный `password`.
* **Ожидаемый результат:** HTTP `201`. В ответе присутствуют `id` и `username`, `id` имеет тип integer.

### REG-002 — Регистрация с существующим username

* **Тип:** Negative, Equivalence Partitioning
* **Предусловия:** Пользователь с указанным username уже существует.
* **Шаги:** Повторно отправить запрос регистрации с тем же username.
* **Ожидаемый результат:** HTTP `409`.

### REG-003 — Отсутствует username

* **Тип:** Negative, Boundary
* **Шаги:** Отправить запрос без поля `username`.
* **Ожидаемый результат:** HTTP `400`.

### REG-004 — Отсутствует password

* **Тип:** Negative, Boundary
* **Шаги:** Отправить запрос без поля `password`.
* **Ожидаемый результат:** HTTP `400`.

### REG-005 — Пустой username

* **Тип:** Negative, Boundary
* **Шаги:** Передать `username=""`.
* **Ожидаемый результат:** HTTP `400`.

### REG-006 — Пустой password

* **Тип:** Negative, Boundary
* **Шаги:** Передать `password=""`.
* **Ожидаемый результат:** HTTP `400`.

### REG-007 — Некорректный тип username

* **Тип:** Negative, Equivalence Partitioning
* **Шаги:** Передать числовое значение вместо строки.
* **Ожидаемый результат:** HTTP `400`.

### REG-008 — Некорректный тип password

* **Тип:** Negative, Equivalence Partitioning
* **Шаги:** Передать числовое значение вместо строки.
* **Ожидаемый результат:** HTTP `400`.

## 3. Создание объявлений

### ITEM-001 — Успешное создание объявления

* **Тип:** Positive, Functional
* **Предусловия:** Пользователь зарегистрирован и авторизован.
* **Шаги:** Отправить `POST /api/1/item` с корректными данными и собственным `sellerID`.
* **Ожидаемый результат:** HTTP `200`. В поле `status` присутствует UUID созданного объявления.

### ITEM-002 — Уникальность идентификаторов

* **Тип:** Functional
* **Шаги:** Создать несколько объявлений.
* **Ожидаемый результат:** Каждое объявление получает уникальный UUID.

### ITEM-003 — Создание объявлений с одинаковыми данными

* **Тип:** Functional, Corner Case
* **Шаги:** Несколько раз создать объявление с одинаковыми параметрами.
* **Ожидаемый результат:** Запросы обрабатываются успешно, объявления имеют разные UUID.

### ITEM-004 — Создание без авторизации

* **Тип:** Negative, Security
* **Шаги:** Отправить запрос без Bearer token.
* **Ожидаемый результат:** HTTP `401`.

### ITEM-005 — Создание с недействительным токеном

* **Тип:** Negative, Security
* **Шаги:** Передать произвольный недействительный Bearer token.
* **Ожидаемый результат:** HTTP `401`.

### ITEM-006 — Использование чужого sellerID

## 10. E2E

### E2E-001 — Полный жизненный цикл объявления

* **Тип:** E2E, Functional
* **Шаги:**

  1. Зарегистрировать пользователя.
  2. Авторизовать пользователя.
  3. Создать объявление.
  4. Получить объявление.
  5. Получить статистику v1.
  6. Получить статистику v2.
  7. Удалить объявление.
  8. Проверить отсутствие объявления.
* **Ожидаемый результат:** Все операции выполняются успешно, после удаления объявление недоступно.

## Использованные техники тест-дизайна

В тестах применялись:

* **Equivalence Partitioning** — корректные и некорректные типы/значения параметров;
* **Boundary Value Analysis** — пустые и отсутствующие значения;
* **State Transition Testing** — создание → получение → удаление → повторный запрос;
* **Negative Testing** — некорректные параметры и несуществующие ресурсы;
* **Security / Access Control Testing** — отсутствие и некорректность авторизации, проверка `sellerID`;
* **End-to-End Testing** — проверка полного пользовательского сценария.
